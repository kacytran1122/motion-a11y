An accessibility checker for animation code

Your linter checks
your HTML. It never
checks your motion.

Some animations make people dizzy. Some flash fast enough to trigger a seizure. Your usual accessibility tools miss both, because they do not look where animation lives: ESLint reads HTML attributes, Stylelint reads CSS, and Axe only sees the page once it has loaded.

motion-a11y reads your JavaScript, finds the risky animations, and names the problem.

    animation written in CSS, and motion-a11y leaves that to it.

The seven rules

  
Every rule comes from
a real WCAG standard.

  

    No opinions about style, and no arguments about taste. Every rule points at a published
    accessibility standard, so you can show your team a rule instead of a preference.
  


  


    

      
require-reduced-motion-guarderror

      
This file animates something, but never checks whether the visitor asked for less motion. Reported once per file rather than once per line, so the output stays short.

      
// no useReducedMotion anywhere in this file
<motion.div animate={{ x: 200 }} />

      
WCAG 2.3.3 Animation from Interactions

    


    

      
no-fast-flasherror

      
Something fades or changes colour more than three times a second. This is the one rule that still reports even when the file does check the motion setting. See below for why.

      
el.animate([{ opacity: 0 }, { opacity: 1 }], {
  duration: 120, iterations: Infinity
});

      
WCAG 2.3.1 Three Flashes or Below Threshold

    


    

      
no-infinite-animationerror

      
Motion that repeats forever with no way to stop it. Add a pause button and it passes, because that is exactly what the standard asks for.

      
gsap.to(".pulse", {
  scale: 1.1, repeat: -1
});

      
WCAG 2.2.2 Pause, Stop, Hide

    


    

      
no-scroll-linked-animationwarn

      
Motion that follows the scroll bar. Roughly 35 out of every 100 adults over 40 have an inner-ear condition, and scroll-driven parallax is the single worst trigger for it.

      
const { scrollYProgress } = useScroll();

      
WCAG 2.3.3 Animation from Interactions

    


    

      
no-long-animationwarn

      
An animation runs for more than five seconds with no way to pause it. Each library measures time differently, so seconds and milliseconds are both read correctly.

      
gsap.to(".hero", { x: 400, duration: 12 });

      
WCAG 2.2.2 Pause, Stop, Hide

    


    

      
no-smooth-scrollwarn

      
A smooth scrolling jump with nothing to fall back on. Found however you write it, including in the middle of a chain of calls.

      
document.querySelector("#top")
  .scrollIntoView({ behavior: "smooth" });

      
WCAG 2.3.3 Animation from Interactions

    


    

      
no-autoplay-lottiewarn

      
A Lottie animation starts playing on its own. Covers the React components and lottie-web, including a bare autoplay attribute.

      
<Lottie animationData={data} loop autoplay />

      
WCAG 2.2.2 Pause, Stop, Hide

    


    

      
Two presets

      
recommended is the default: some rules fail the check, others only warn. strict makes every rule fail. You can change or switch off any rule.

      
motion-a11y src --preset strict
motion-a11y src --rule no-smooth-scroll=off

      
Run motion-a11y --rules to print the table

    


  







  
One deliberate exception

  
The flash rule ignores your motion setting.

  

    Every other rule goes quiet once your file respects the visitor's motion setting.
    no-fast-flash does not, and that is on purpose.
  

  

    Most people who are sensitive to flashing have never turned that setting on, and many do not
    know it exists. A seizure risk is not a preference to honour, so the rule asks you to slow the
    flashing down rather than hide it behind a setting. If you disagree about one file, switch the
    rule off there by hand. Then it is a decision somebody made and can be reviewed.
  







  
How it spots your check

  
What counts as asking
for the motion setting


  

    

      

        Your file passes if any of these appear in it. They are read from the real structure of your
        code, not by searching the text, so writing one in a comment will not fool it.
      

      

        The check is per file, not per function. So a file that checks the setting in one place and
        animates without it somewhere else still passes. That is on purpose: false alarms are the
        fastest way to get a tool switched off, and a tool nobody runs finds nothing.

Three ways to run it

  
Same rules.
Pick where you want them.


  

    

      One
      
On the command line

      
Point it at a folder and it does the rest. It skips node_modules and build output on its own, and it fails when it finds an error, so you can put it in a pre-commit hook.

      
npm i -D motion-a11y

npx motion-a11y src

    


    

      Two ★
      
In your pull requests

      
Add one line to your workflow and every problem shows up as a comment on the exact line that caused it. Reviewers see it without opening any logs.

      
- run: npx motion-a11y src \
    --format github

    


    

      Three
      
From your own code

      
Full TypeScript types, and it works with both import and require. A file it cannot read is reported, never thrown, so one bad file cannot break your build.

      
import { lint } from "motion-a11y";

const r = lint(src, {
  filename: "Hero.tsx"
});

    

  







  
What it does not do

  
A tool is only worth
keeping if it is honest.


  

    

      
It does not read CSS

      
Animation written in a stylesheet is Stylelint's job, not ours. Run both tools. They do not overlap.

    

    

      
It does not judge style

      
Only the things you can measure: how fast, how long, how often, and whether you checked the motion setting. Whether it feels nice is a human call.

    

    

      
Numbers must be written out

      
duration: SPEED cannot be worked out without running your code, so it is skipped rather than guessed at.

    

    

      
It checks per file

      
Not per function or per component. This keeps false alarms low, at the cost of missing a file that does both.
